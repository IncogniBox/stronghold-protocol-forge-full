# 模式扩展-重构模拟（mode-recon）

「重构模拟」的工坊包。模式本体不走本包 —— 大厅入口（仅本地客户端可见）、房间分队（1~5 队、每队至多 4 人；新加入的博士与 AI 会自动落到第一支未满的队伍，编队容量满了就不再放人）、预重构阶段（PRE_RECON，60s）与 20 回合结构由引擎在运行时合成（`shared/reconModes.js`，不落盘 `data/config.json`）。

本包带这几样东西：

1. 附加盟约【重构】（`bond_recon`）的占位记录 —— 预重构阶段的盟约倾向与后续的【重构协议·特训】都要引用这个 id，先落一条无战斗效果的记录把引用链闭合。
2. 【重构】的图标（`assets/bond/icon_recon.png`，`pack.json.bondIcons`）—— 盟约圆盘（预重构 / 盟约条 / 盟约详情）画的就是它。
3. **对局元载荷**（`server.meta` → `meta/main.mjs`）：预重构交上来的两项选择里属于**休整期**的两条 —— 盟约重构（`<修整期结束时>` 三类盟约各 +10 层）与装备重构（每回合前 3 次销毁装备时补一件不低于其阶级的随机装备）；外加装备负载的**倒计时**（装备阶级高于携带者 → 3 回合后 `ctx.destroyItem` 销毁）。
4. **战斗侧载荷**（`server.battle` → `battle/main.mjs`）：另外四条 —— 数据重构（我方基础攻/防/生命上限 +25%、法抗 +25）、数据负载、盟约负载（三类最高层盟约每层抬敌生命上限 0.1%）、装备负载的战斗部分（未携带装备伤害 -25%；高阶级装备效果 -50%）。
5. **二十九名·重构首领**（`enemies.json` + `battle/main.mjs`）—— 官方首领的变体（第 4 回合：碎骨·重构 / 庞贝·重构 / W·重构 / 泥岩·重构 / 鼠王·重构；第 8 回合：凋零骑士·重构 + 腐败骑士·重构（一对）/ 自在·重构 / 梅菲斯特·重构 + 浮士德·重构（一对）/ 杰斯顿·威廉姆斯·重构 / 霜星，“冬痕”·重构；第 12 回合：塔露拉·重构 / 锏·重构 / 爱国者·重构 / “复仇者”·重构 / 狂躁异质裂兽·重构；第 16 回合：蔓德拉·重构 / 血骑士狄开俄波利斯·重构 / 莫菲丝·重构 / “酒神”·重构 / “望”·重构；第 20 回合（最终首领）： “不死的黑蛇”·重构 / 奎隆，摩诃萨埵权化·重构 / 伊莎玛拉，腐化之心·重构 / 玻利瓦尔，症结之核·重构 / 朔壳·重构；另有保留的萨卡兹百夫长·重构），详见下面各节。
6. **两条召唤物记录**（`enemy_ws_recon_bldbld` 凝血之刃 / `enemy_ws_recon_xia` 瑕）—— 记录与素材留在包内供普通版（`workshop/enemy-ext`）复用；宿主（血骑士 / “望”）的重构版已移除，本包代码不再召唤它们。
7. **官方战斗特效接线**（`battle/main.mjs` 的 `castSkill()`）—— W 的 C4 开火时发 `['cast', id, slot]`（引擎 `content/enemies/helpers.js` castSlot 的包侧版本，display only），客户端据此打开那个技能的**官方特效窗口**（skillfx）。特效文件本体**不在这里**：28 个基座的官方 fx 精确闭包由 `workshop/enemy-ext`（`pack.json.fx.manifest`）携带，与本机提取合并（包优先）。
8. **重构模拟的专属战场**（`stages.json` / `stage-specs/my_map.json`）：地图 id `my_map`，正式名称 **重构战场01·天镜阁**（45×60，主题 `skymirror`，四块 boss 场地：主 boss 场 + 左 / 右 / 下三块，每块两位棋手左右或上下分半）。它的 `modes` 声明 `mode_recon_abyss`（**只保留终极难度**，业主 2026-10-27 移除了其它三档；模式本体与难度曲线在 `shared/reconModes.js` 运行时合成，不落盘）；引擎的 `shared/workshop.js linkWorkshopStages` 会把声明了某个 `mode_recon_*` 的工坊地图挂进该模式的战场池，并**只保留这些声明过的地图**（合成时从 `mode_multi` 继承来的官方地图不再参与）—— 所以重构模拟目前只会在这一张图上开打。**整备区按地图自己的格子**（`layout.bench`，引擎 `shared/layout.js benchOf`）：普通带与四块 boss 场地的每一位棋手都是 **16 格整备区（2 行 × 8 格，地图上的 `a` 格）+ 8 格临时整备区（手牌两行外侧那一行 8 格）**；官方地图没有这份声明，仍是 10 / 5。**敌人的行动路线也按地图自己画的 16 条走**（`routes`：普通回合 8 条 = 左 4 / 右 4，各 2 地面 + 2 空中；**boss 区域 8 条 = 四块场地各 2 条，起点就是首领站位中心、终点回到起点（闭环）**）：普通回合的整张路线表只用前 8 条；boss 回合的**首领与部位**改走各自那块场地的两条（起点 = 中心、闭环巡逻，**走完一圈回到起点继续，不算漏怪**），**护送小怪 / 悬赏敌人**的模板路线（官方 19×21 板上画的）按比例**缩进这块场地的战斗矩形**（否则会落在地图外、被 sim 夹到边缘蹭边界）。**站定不动的首领**（源阶方 / 岁四部位 / 洛伦茨）另带 `recon:boss_still`（`noMove`），路线只用来把它们的出生点定在中心。普通带双人同场时每个半场各一份出怪，等待区里看到的怪物只走自己那半场的路线、只攻自己那半场的门，漏怪也按半场记到那位玩家头上（`server/match/waves.js routeSpawn` / `combat.js _normalPairOpts` / `views.js nextEnemiesFor`）。

选择本身留在服务端 `Match.reconChoices`（预重构阶段落的账）；元载荷用 `ctx.recon()` 读它，再物化成一条 `EffectRef` 交给战斗侧（`playerEffects`）。

## 预重构的三条口径（引擎侧，本包不参与）

2026-10-26 / 27 业主在预重构里定了三条**引擎级**规则；本包没有代码参与，只在这里记下口径，免得把引擎行为当成包的问题：

- **自主禁用盟约**（`g.reconChoice.ban`，每名玩家至多 1 个）：判据与官方「本局禁用盟约」同一条 —— 一枚棋子身上**每一种盟约都被禁**（本局抽签禁用 ∪ 模式静态禁用 ∪ 自己禁的那一个）才从**这名玩家自己的抽卡**里消失。配对共享池里的拷贝、队友的抽卡、盟约本身的战斗效果都不动；自选编队的库存也在预重构结束时按同一条判据重算。实现：`server/match/match/reconPools.js` + `player/rules.js` 的 `mainPool()` 只读视图。
- **同场配对共享卡池**：不再是全房间共用一个棋子池，而是**普通带同场的一对**（存活座位两两配对，与 `normalGroups` 同一条顺序）共用一个 `SharedPool`；配对在开局定下、整局不变。`m.pool` 退居为只读目录（审计 / 不变量仍读它）。
- **盟约倾向改抽卡概率**（2026-10-27）：主 / 副 / 故事集盟约被选中后，**自己干员的出现占比提高**，同组其余盟约平摊同一份降幅 —— 组内概率总和恒为 1。总提升：**核心 10% / 附加 20% / 故事集 10%**（官方 8 条核心选 1 条 ⇒ 所选盟约干员 ×1.8、其余 ×0.886；选 2 条各 +5%，即 ×1.4）。**组内条数取自合并后的盟约表**（`gd.bondIds`，含工坊包新增的盟约：本机装了 rimbilliton / ave-mujica / columbia / dossoles 时核心是 11 条、所选倍率 ×2.1）—— 与预重构屏的候选池同一条名单，mod 新增的盟约同样参与分摊，mod 棋子同样带权重。一条盟约的倍率 = 调整后份额 ÷ 原份额，**干员权重 = 它携带的各盟约倍率的平均**（多盟约只吃部分提升；没交倾向时权重恒为 1，抽卡与原版逐字节相同）。作用点是 `mainPool()` 的 `roll` 视图（商店 / 晋升与合成奖励 / 内容 `rollChess`），池里的拷贝与队友都不动。实现：`reconPools.js` 的 `reconBondLeanWeights` + `pool.js roll` 的可选 `weight`。
- **队伍预重构总览**：全员交齐后阶段仍停在 `PRE_RECON`（`recon.summary`），客户端播过场并展示**本房间队伍**的选择总览；每位在场真人点「继续」（`g.reconContinue`）后全齐才进入下一阶段。计时耗尽也会先切总览，并留 15 s 兜底。
- **协助 / 负载没选就随机补 1 个**（业主 2026-10-29）：两项选择缺席时不再等于「没有效果」—— 进入总览时 `Match.fillReconChoices` 给每个座位各抽一个（六个合法 id 见 `shared/reconModes.js` 的 `RECON_ASSIST_IDS` / `RECON_LOAD_IDS`），已选的保留；随机数走每人一口独占流（同一 seed 可复现），补选后的值随 `pub.recon.choices` 下发，本包 `ctx.recon()` 读到的就是它。
- **本局信息入口**（业主 2026-10-29）：策略选择屏左侧的「查看禁用盟约与干员」现在在预重构屏的左侧状态列也有一个（同一条 `ui/matchInfo.js` 的 `MatchInfo` / `MatchInfoDialog`，模型与简报同一份）；弹窗底部的状态行显示自己的提交状态与「全员提交后进入队伍总览（n/m）」。

## 五名·重构首领

第 4 回合的五个 key 是**官方首领的变体**：`enemies.json` 里那条记录**逐字照抄**官方记录（`data/enemies.json` 里对应的那一条），只动四处 ——

1. `key` = 新的 key（必须等于 JSON 的映射键）；
2. `name` = 官方名 + `·重构`；
3. `abilities` = 官方那几条**原样保留**，末尾**追加一条** `【重构】…`（业主给的原文）；
4. （W 除外）写上 `effectRef` = 官方基座的 key。

`spine` / `iconId` 沿用官方的值，所以真模型与真头像照画；其余字段（数值、天赋 bb、技能、`be` / `attrPower` 这些推导量）一个字节都不改 —— 手动改这些推导量会被 `validateEnemy` 报 `STALE_DERIVED`。

**为什么要写 `effectRef`（本包能零引擎改动做出「·重构」首领的唯一通道）**：引擎在敌人出生时用

```js
const kit = KITS[e.def.raw?.effectRef ?? e.defId];   // server/sim/content/enemies.js:176
```

取 kit，而 `e.def.raw` 就是**这条记录本身**（`server/sim/simdata.js:304` 的 `raw: e`）。于是只要记录带一个 `effectRef` 指向官方 key，它就**免费继承官方首领的整套 kit** —— 不需要在 `server/` 里加任何一行，也不改官方数据。本包的 `battle/main.mjs` 只负责把「·重构」那一条机制**叠加**上去。

### W·重构 为什么没有 `effectRef`

官方 W 的 kit（`server/sim/content/enemies/leaders.js:126-138`）把 C4 的目标数**硬编码**成 `n = hpRatio < 0.5 ? 2 : 1` ——「不许改引擎」意味着那一行动不了。于是 W·重构 **不写 `effectRef`**、C4 整个由本包实现（官方 W 的 kit 里**只有** C4，所以没有别的东西会丢）。记录里把 C4 的 `cooldown` **减半**（20 → 10）、`initCooldown` 不动（9），本包把那个数读出来当自己的计时器。

### 已知的近似（别当成 bug）

- **W·重构 的索敌顺序**：引擎的 `targeting.js sortAllyTargets` 是「阻挡者 → 仇恨值（嘲讽 / 最晚部署）→ 最早出现」，本包用「**阻挡者优先 → 距离最近**」近似 —— 少了嘲讽与部署序两个键。
- **C4 的溅射范围**：引擎用 `areaAllies`（隐匿 / 无法选中 / 起飞 都排除），本包用 `alliesInRadius` + 排除飞行与无法选中，但**被锁定的那个目标一定吃到**（与引擎的 `targetAndArea` 同一条：锁定目标不因之后的选择规则被排除）。
- **碎骨·重构 只处理「被阻挡」的那一路**：官方 kit 已经在「未被阻挡」时发射榴弹（`splashAttack`），本包叠加的是「近战再多一发」。
- **引擎的 `applyStatus('defDown', { value })` 收的是正数减益量**（`server/sim/buffs.js:115`），而数据里的 `defdown.def` 是 −0.5，所以本包取反后再传 —— 与引擎 `leaders.js` 的 `dd` 一字不差。

## 重构协议·特训（已落地）

每个特训回合（4 / 8 / 12 / 16 / 20，`shared/reconModes.js RECON_TRAINING_ROUNDS`）的**休整期**，重构对局的**调度中心工具行**多一枚「特训」按钮（`ui/shopBar.js` 的 `train` 槽，紧挨冻结 / 刷新；荧光青 `--mint-400` + `public/icons/recon-train.png` 的蒙版图标；`screens/game.js` 传参）：弹窗（`ui/reconTrain.js`）里从**场上与待部署区**各点一名干员——前者教官、后者学员，交新 C2S `g.reconTrain { mentor, trainee }`（`shared/protocol.js` → `intents.js` → `PlayerState.reconTrain`，`player/prep.js`）。每名博士每个特训回合一条，重交覆盖同回合那条。
本回合交过之后按钮**仍可点开**（画成已完成）：弹窗预填当前那一对，可换人或交 `g.reconTrainCancel { trainee }`（`PlayerState.reconTrainCancel`）**取消本回合特训**——关系条目一撤，战斗输入就不再带 `reconTrainee`；学员 `meta.data.bondGrants` 只回收**这条关系实际加进去的**那几条（授予来源记在 `meta.data.bondGrantSrc['recon:<回合>']`），装备继承等其它来源原样保留。

- **继承口径（叠加式，2026-10-27 定稿）**：学员的战斗输入条目带 `reconTrainee = { chessId, loadout, diy?, ratio, skin? }`（`player/round.js battleInput`），sim 侧 `DataSource.getChess` 的 `traineeOf` 组成通道（`server/sim/simdata.js getTrainee`）据此组出一条 def。
  - **基础数值**：攻 / 防 / 生命上限 = **学员自己的 + 教官的 ×0.5**（`RECON_TRAINEE_STAT_RATIO`；同一学员只叠一层，**链式**见下）。
  - **属性 / 攻击范围**：再部署时间、部署费用、阻挡数、攻击间隔、攻击范围**全是学员自己的**，教官的一概不继承也不融合。
  - **天赋**：学员原有的照常结算，教官的天赋 installer **追加**到学员的 kit（`content/index.js applyTraineeMentor`）。
  - **特质**：`PlayerState.pieceGarrisonIds` 把学员自己的 `garrisonIds` 与教官的并起来——休整期的 `_garrisons` / `triggerGarrisons`、内容钩子的 `garrisonsOf`、战斗结果校验（`fields.js layerAllowanceOf`）与战斗侧 `raw.garrisonIds` 读的是同一份集合；自己的照常，教官的整备 / 作战能力也叠加。学员原有的照常，教官的 `install` 链在学员之后、`trait` 覆盖对象并入（学员自己的键优先）。
  - **技能**：学员释放自己的技能不变，教官选定技能的**效果**作为影子并进学员的 spec（`mergeShadowSpec`）——数值 mods 相加，但 `batPct` / `aspd`（攻击间隔）、`rangeExtend` / `targeting.rangeGrid`（攻击范围）、技能持续时间、弹药数、SP / 触发规则全是学员自己的。攻击侧四种组合统一成一条语义（业主 2026-10-29 修频率）：**学员造成的每一次伤害都同步 1 次教官技能的攻击效果**——多段攻击按段数（一次攻击 4 段伤害 ⇒ 4 次教官效果），`attack.hits = 学员自己的段数 × (1 + 教官的段数)`（教官 1 段时即原来的 ×2；赤刃明霄陈 S3 这类「每次普攻 3 次攻击」的技能 ×4 —— 教官改掉的**攻击次数**一起继承；`hitsFn` 现算段数的 kit 按同一式）。学员自己的技能没有 attack 行时，教官那一套直接作为它的攻击（段数照教官的）。**攻击目标选择数量**（`targeting.maxTargets`，逻各斯 S3 的 `attack@max_target` 这类）取大并入。**攻击命中的附带效果**也一起继承：`attack.afterHit`（维什戴尔 S3 的余震 / 好礼爆炸就是这个形状）、`attack.onEachHit`、`attack.onHit` 链式接上。**单次释放类教官技能**（本体没有 attack / mods / targeting、效果全在一次 `onStart` 里生成，异客 S3 辉煌裂片的雷暴就是这一种）继承后改为**学员每次攻击各触发 1 次**（业主 2026-10-29：与弹药类相似，不再只在施放时触发一次），浮游单元的每次命中同样各触发 1 次（`installMentorApply` 走同一份）。学员 kit **自己直接结算**的伤害（浮游单元的每一次命中、技能 DoT 的 tick 这类不走 `resolveHit` 的实例）本来吃不到段数翻倍，`installMentorApply` 给它们补一次教官的攻击应用（一整套教官攻击：`hits` 段「ATK × 教官攻击倍率」的伤害 + 教官的 `afterHit` / `onEachHit` / `onHit`）；学员自己那一次攻击的伤害（`isAttack` / `isSplash` / 带 `attackId`）已由段数与溅射覆盖，跳过。
    - (1) 非弹药 × 非弹药：每段伤害多一整套教官攻击（学员 2 段 × 教官 1 段 → 4 段；教官 3 段 → 8 段）；
    - (2) 非弹药 × 弹药：同上（教官的弹药上限不跟过来，每次攻击都触发）；

### 2026-10-28 “不死的黑蛇”动作与全屏火雨（0.19.19–0.19.20）

业主：「“不死的黑蛇”动作有问题，和特效对不上，而且全屏火雨的技能还是没有实现」。三条根因都在**动作**那一侧：

1. **普攻附带的【烈焚灼息】发了技能**：`bsnameFire` 每次都 `castSkill(Ignite)` ⇒ 首领**每一下普攻**都把技能槽
   点亮到 1（模型切 Skill_1_A 的施法动作、SKILL 旗亮 0.3 s），普攻的挥砍被截断。现在只有「周期性点燃两名我方」
   那一次施放（`Ignite`）走技能，攻击附带的那条是纯被动（与官方「攻击造成真实伤害并对目标施加【烈焚灼息】」一致）。
2. **不息恶火每轮都施放技能槽 3 并逐目标发 `atk`**：官方 `ScreenAttack` 是**模式**不是技能动作（`anims.skills`
   槽 3 的 `animKey` 是空的），于是客户端退回上一次的技能动作（Skill_1_A）；逐目标的 `atk` 又让首领每轮挥 7 次
   普攻。现在整段**一条都不发**（首领在无敌窗口里站着，`noAttack`），火雨由 FX 层画。
3. **火雨本身没画出来**：那条 `beam` 的 `from` 是**坐标**而不是单位 id，客户端只把它降级成目标身上的一枚火星；
   官方真正的全屏画面 `screen_bsnake`（`Modes/ScreenAttack` 的 `GlobalAuraAbility`，本包 `fx.manifest` 已携带）
   则没有任何通道能播。

改法：

- **引擎新增 `official` fx 种类**（`public/js/render/fx/kinds.js` + `simfx.js _officialFx`）：
  `battle.fx('official', { x, y, key, holdS, id })` 在官方特效层里按 key 起**一枚** prefab、撑满 `holdS` 战斗秒再收
  （同 `(id, key)` 只一枚，重放 / 追帧不会叠第二份；官方特效关着 / 没有这枚 prefab 时什么都不画）。这是此前客户端
  唯一缺的那条「按名字播官方 prefab」的通道（官方的全屏效果只能由引擎写死 key，如陈 S3 的 `qi`）。
- **不息恶火**：整段起一枚 `screen_bsnake`（`holdS` = 10 s + 0.6 s 收尾）；每 1 s 一轮 —— 全屏火光
  （`telegraph` r ≥ 12 档 = 闪屏）+ 16 处空地上的火（按轮次错开地铺满整个战场、从火源那一侧往另一侧，确定性地取格，
  不掷随机）+ 该行最靠近火源的我方身上的火团；伤害口径不变（`atk + 230` 法术，逐行一人）。官方特效关掉时这一层
  就是全部画面。
- 火团**不带 `id`**：客户端 `_flame` 按 `src` 认「同一股火」，带 id 会把一轮的所有命中并成一股。

**0.19.20：再提取一遍官方那枚特效，修位置。** 业主「火雨的特效有点问题」——用 `tools/local-extract/extract.py
--only fx --fx-keys screen_bsnake` 从本机客户端重新导出：**prefab 与本包那份逐字段相同**，6 张 tex
（`fire_29` / `flow_11` / `flow_13_m` / `star_02` / `star_09` / `Default-Particle`）+ 2 个 mesh（`Plane001`）本包也全有
⇒ **素材不缺，问题在摆位**。剖析这枚 prefab：

- 它是 `ScreenEffectEmitter._effect`（`GlobalAuraAbility` 的 `EffectAura`，`by: name`），由**屏幕特效发射器**起，
  不是挂在自己/目标身上的那种。prefab 根是 `EmptyEffect`，`static_offset` = `[7, -2.1, -9.78]`、俯 −30°（正对战斗
  相机的 30° 倾角），里面三块：`andi`（5.8×10.8 的暗色全屏片，`Torappu/Particles/AlphaBlend`，黑 33%）、
  `liudong`×2（扰动片，`Disturb Origin`）、`fire_1` / `suduxian` / `liang`（火焰 / 速度线 / 亮斑）。
- 也就是说这枚 prefab 自带了「抬高约 9.8 格、俯 30°」的**摆位**，它要起在**战场中心**才会摊在整个战场上。
  0.19.19 里客户端把它起在**世界原点**（`tile (10,9)`）—— 用引擎自己的 `presetCamera('boss')` 投影核算：整片火会偏到
  战场右上、暗色片的 y 全在屏幕上方（−625…−10 px），这就是「有点问题」。现在改为**起在战场中心**（`fx` 的 x/y），
  同一条投影核算下火焰落在屏幕中部、暗片压在战场上。
- 仍要说明的边界：这枚 prefab 是官方**相机空间**的特效（客户端 `ScreenEffectEmitter` 挂在屏幕层），本引擎没有
  屏幕层，只能当世界物体播；位置足够接近，但**不是**逐像素还原。官方特效关掉时整段只有程序化火团。

## 注意

- 入口与建房在服务端有本地闸：非本机（loopback / 私网）客户端建不了重构模拟房间。

- 元载荷只在**本模式**的房间闹事：`ctx.recon()` 为 null 时它一个动作都不做（非重构房间照旧）。
